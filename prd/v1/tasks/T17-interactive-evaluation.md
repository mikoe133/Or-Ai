## 子任务

- [ ] T17.1 先明确情绪/理解目标，再为首个玩法定义输入、操作/确认、完成、评估与配套报告解释，说明这些选择能提供何种观察/行动线索；建议先排序或分配。分支/动作/计时按独立玩法验收，不用无依据行为推断关系结论。
- [ ] T17.2 定义版本化的 discriminated union 答案/事件 schema 与能力注册，新增独立 engine key；现有 questionId/optionId 和 dimensions_v1 契约保持兼容，不用任意 JSON 绕过校验。
- [ ] T17.3 实现对应服务端合法性/完整性检查：如排序无重复/遗漏、分配总量与边界、分支可达路径与条件；客户端不能自行宣告完成或结果。
- [ ] T17.4 实现可重复的评估器、结果/报告投影、边界与不适用规则；生成报告、消费次数和结果贡献仍原子提交，重复/并发完成返回同一结果。
- [ ] T17.5 为该玩法保存权威任务/试次状态、修订、事件序号或答案快照，处理刷新/暂停/断线重试和过期/撤权；如使用计时，先固定服务端起止与网络影响/精度说明。
- [ ] T17.6 定义玩法对应的群体反馈、分母、版本/体验分组与样本不足策略；无可比“单选分布”时返回明确的不适用/专用反馈，不伪造百分比。
- [ ] T17.7 接入一个可复用网页小游戏模板与受保护的规则/内容制作入口，选择相应 experience/assessment skill；按契约保存内容、体验与评估引用，不把脚本作为配置执行。
- [ ] T17.8 用真实本地业务库验证首个玩法的输入边界、伪造/陈旧/重复事件、路径或预算约束、恢复、并发完成、统计及原商品回归；未选或未实现玩法逐项保持待开发。

## 交付与验收

一个明确玩法对应的标准输入协议、后端评估器、前端游戏模板、报告/统计与恢复证据。每新增一种评估机制都追加独立契约与验收，不能以首个排序玩法通过宣称反应时间或任意游戏均已支持。

游戏商品首期仍沿用报告成功生成后消费的交付规则；无报告的纯游戏、多人实时互动和奖励/竞技等机制需另定义交付与运行范围。
