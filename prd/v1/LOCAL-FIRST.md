## 本地阶段安排

先补 T06-O 的实际操作环境，再按 T12-A/B/C → T13 → T14-L 建立内容制作链；随后推荐做 T15 → T16-A，再接 T10-L 正式视觉。Three.js 与新评估玩法留后续队列，不必一起开发。

推荐排期和技术依赖分开：T06-O 暂未配置时，T12-A 的模型/API/隔离测试可继续；T15 基础只依赖 T05/T08，后台/机器 authoring 在 T12–T14-L 后补齐；T16-A 可先验人工配置的运行样例，完整机器制作另验。若优先上线已有单选商品，可在内容制作链之后先进入 T10-L/T09，扩展继续留队列。

T12–T14 的 M7、T15/T16 体验扩展与原 M5/M6 分别验收；不把新增技术变成原平台/首款销售的必要门槛。T10-L 可先于 T09，但整体 T10-V/M5 需要正式 UI 和公网业务链共同通过；未启用 T14-C 不阻塞原平台验收。

## 如何实现和验证

- 前端继续 React/Vite＋Tailwind 3.4，同一套响应式页面共用 API/状态，正式稿接入不重写已验业务逻辑。
- NestJS/Prisma 使用真实本地 PostgreSQL，继续受限运行账号、商品版本/报告快照/权益与退款事务；新能力用向前迁移，不 reset 数据或重写旧迁移。
- T06-O 使用真实本地 Supabase Auth 和本地收件工具，认证存储与业务数据隔离，保留稳定密钥与可重复启停。权限仍由真实用户、邮箱和数据库 ADMIN 校验，不能用 seed ID、请求头或测试按钮取得管理员权限。
- 文件通过存储适配器读写：本地受控目录、数据库受控引用，运行/生产不依赖容器临时磁盘；实际文件验证、历史引用与恢复要有证据。
- T12 共用商品创作设定，固定题目/文案/封面/视频的修订与使用快照；新报告方案独立保存为版本化草稿，运行投影/renderer 归 T15，旧兼容报告先完成采用链。
- T13 保存四库 skill/版本/附件/绑定；T14-L 提供四份独立领域配置，共用受限授权服务与真实流式上传。skill 内容不在后台安装或执行。
- T15/T16 先保持单选输入与既有后端评分，运行模板/报告形式、资源和恢复另外版本化；T17 有明确玩法时再扩展答案 schema/评估。
- 样例商品/价格/报告明确为演示；没有真实身份/邮件/对象存储配置时如实记录，不将隔离测试写成云端通过。
